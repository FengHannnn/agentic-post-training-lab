# 困难恢复定向加权 SFT：结果审阅

日期：2026-11-03。
运行：hard-recovery-sft-weighted-v1-20261103。

本轮加权续训明显改善了困难恢复行为。最终模型在开发上下文的随机有效恢复由 37/84 提高到 74/84，完整开发任务随机成功由 11/16 提高到 15/16。第4轮起，训练集 greedy 的三类 SQL 重查全部通过目标验证；最终训练／开发 greedy 的目标验证分别为 36/36、12/12。主要剩余问题是检查失败后的数值修正，以及完整轨迹中两个指标同时未验证时的恢复。

本地审计通过：64 条完整轨迹、508 步、896 次初始／最终恢复动作和420次中间检查点动作，均已重放并复算汇总。结果基于本次运行内的前后配对。

## 关键工具token发生了什么变化

沿用上一轮分析方法，读取训练前后保存的FP32逐token分数，在每个训练上下文中提取JSON工具值的首token概率；每类12个不同上下文。greedy选择由本轮BF16原生生成记录核对。

| 场景 | 正确首token | 训练前平均概率 | 训练后平均概率 | 最终greedy工具一致 |
|---|---|---:|---:|---:|
| SQL未验证后重查 | query | 2.87% | 89.57% | 12/12 |
| 重复证据错误后恢复 | query | 10.35% | 88.18% | 12/12 |
| 连续SQL错误后重查 | query | 99.84% | 99.997% | 12/12 |

此前正确query分支概率偏低的问题在本轮显著改善，greedy动作也随之改变。连续SQL错误场景中工具本来就较明确，本轮同时学会了生成能通过验证的SQL。检查修复的工具分支已稳定，余下错误集中在参数值。

本轮包含场景加权与新增258次续训；上述指标记录这次整体训练后的变化。

## 剩余失败与下一步

最终greedy失败为：

- train-001:failed_check_repair：正确差额-9604，仍提交-9603。
- train-004:failed_check_repair：正确差额-5257，仍提交-5256。
- development-000:failed_check_repair：正确差额-1843，仍提交-1842。
- development-001:failed_check_repair：差额仍为注入后的错误值。

这些动作选择了正确的check_result，证据ID也有效，仍保留上一条错误差额。下一批数据可重点要求从calculate_change观测中的正确值恢复提交参数。

完整开发随机评测剩余1条失败为development-001/rollout3。两个SQL查询都未通过验证，模型随后连续7次calculate_change。该轨迹的退款JOIN额外按订单月份筛选，漏掉跨月订单的当月退款。已有的 sql_unverified_requery 与 repeat_evidence_error 上下文均为当月未验证、上月已验证；这条轨迹中两个查询均执行成功却未验证指标的组合，可作为后续扩充重点。

建议下一步进入独立测试集评测，覆盖完整任务与困难恢复，并重点检查：

1. 两个月度指标同时未验证时，能否依次重查。
2. 检查失败后，能否以正确证据中的差额替换错误值。
3. 正常任务流程与SQL口径在新任务上的表现。

最终模型登记为已审阅候选，进入独立评测；本轮训练使用train，评测使用train/development。
