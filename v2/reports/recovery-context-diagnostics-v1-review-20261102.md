## 关键工具 token 分析：为何平均 CE 下降但工具仍选错

复用 chosen-only SFT 训练前后保存的逐 token 分数，对每个训练上下文取一条记录并去重，检查 JSON tool 值的首个 token。84 个上下文在该 token 之前的正确回复前缀与本轮 greedy 输出前缀均一致。

下表为训练阶段保存的 FP32 teacher-forced 概率；greedy 工具选择来自本轮 BF16 vLLM 生成。

| 场景／12 个训练上下文 | 正确工具首 token | 训练前平均概率 | 训练后平均概率 | greedy 工具一致 |
|---|---|---:|---:|---:|
| SQL 未验证后重查 | query | 0.0063% | 2.87% | 0/12 |
| 重复证据错误后恢复 | query | 1.63% | 10.35% | 0/12 |
| 连续 SQL 错误后重查 | query | 99.15% | 99.84% | 12/12 |
| 检查失败后修复 | check | 0.48% | 44.82% | 11/12 |

以 train-000:sql_unverified_requery 为例，训练后正确 query token 的 FP32 概率为 3.05%；本轮原生 greedy 选择 calculate，其记录概率为 97.40%。训练确实提高了正确分支概率，当前位置的选择仍明显偏向旧计划。

这组分数将此前的解释进一步落实到具体位置：整段平均交叉熵可以较低，同时工具决策位置仍给正确 token 很低的概率。训练序列中大量后续 token 依赖正确工具前缀得到监督，自由生成时第一处分支错误就改变了动作。

连续 SQL 错误场景的工具 token 概率已很高，SQL 内容仍失败；检查修复的工具选择已经明显改变，具体数值仍容易照抄。因此后续训练需要分别处理工具分支、SQL 改写、错误数值修正。

## 下一步训练建议

优先做困难恢复定向 SFT，保留已有正常流程与容易恢复场景，重点提高以下样本的训练权重：

1. 当前月度指标未验证时重新查询，覆盖初次未验证与重复证据错误两类上下文。
2. SQL 报错后改写为可验证的源表查询。
3. 检查失败后按正确证据修正具体数值。

下一轮按检查点跟踪训练上下文的 greedy 工具选择、目标 SQL 验证、差额修复，再同步观察开发集。先把原样训练上下文中的困难动作学稳，随后扩展任务与错误上下文多样性。

如果场景加权后关键工具 token 概率仍偏低，再单独测试关键 token 加权。分步验证有利于判断每项改动的作用。本次仅完成诊断，尚未启动新的训练。
